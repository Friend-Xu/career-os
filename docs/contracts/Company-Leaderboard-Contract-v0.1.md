# 公司适配榜契约 Company Leaderboard Contract v0.1（草案）

> 状态：**v0.1 草案**（2026-08-16 起拟，待用户评审）
> 来源：用户需求「城市×行业公司榜单，按序投递，避免无头苍蝇」+ 断链审计后讨论收敛
> （榜单位置 / 匹配因子口径 / 检索 skill 分工 / 数据源双通道 / 天眼查 MCP 借鉴）
> 定位：公司空间第三视图——与「列表」（明细查阅）、「地图」（空间直觉）并列，
> 榜单 = **顺序直觉**（先投谁、后投谁）。工作台 Dashboard 提供深链入口。

## 核心原则（口径总纲）

1. **适配榜，不是客观榜**：排序依据 =「对当前人的匹配」，不是公司客观强弱。
   榜单不回答"哪家公司最好"，只回答"**对你，先投哪家**"。
2. **榜单不产生新事实**：只聚合排序。候选池 / 公司档案 / 岗位线索三层数据
   由各自 Producer 产生（见 §2），榜单消费、不写。
3. **排序是确定性规则**，不现场 AI 打分。每个排序因子可解释、可展示。
4. **诚实原则**：样本少说样本少、空网格显式可见、过期线索标注——
   "避免无头苍蝇"不等于"被不完整榜单误导的苍蝇"。
5. **投递是用户事实**：Agent 给线索与顺序，不替用户投递、不自动抓 JD 入库。

## 1. 定位与三层数据

```
company-screener（发现层，现有）  → 候选池（结构化登记，§2.1）
        ↓ 用户点「发起尽调」
company-research（评估层，现有）  → 公司档案 + rating 回链（§2.2）
        ↓
company-jobs（线索层，新增轻量）  → 岗位线索（§2.3，14 天过期）
        ↓ 用户手动递交 JD（现有链路不变）
投递（现有投递闭环）
```

- **候选层**：screener 捕捉、未尽调的候选（候补段，动作 = 发起尽调）
- **档案层**：已尽调、有 rating 的公司（主排序段）
- **投递层**：名下已有用户递交 JD / 有效岗位线索的公司（投递动作可用）
- 同一公司按状态落一层；状态推进（候选→档案→投递）由用户动作驱动。

## 2. 数据模型与 Producer Ownership

### 2.1 候选池条目 CandidatePoolEntry

| 字段 | 类型 | Producer | 说明 |
|------|------|----------|------|
| `id` | candidate_{date}_{seq} | **Engine 登记** | 系统命名，Agent 无权 |
| `name` | canonical 公司名 | **Engine 登记（锚定后）** | 实体锚定铁律：先锚定再入库，防同名/子公司错认 |
| `city` | string | Agent 检索（外部事实） | 带来源 |
| `industry` | string[] | Agent 检索（外部事实） | 行业桶，可多值 |
| `signals` | {tag, source, date}[] | Agent 检索（外部事实） | 资质/融资/招聘等信号，每条带来源+日期 |
| `fit_stars` | 1-5 | Agent 打分（**AI 推理**） | screener ★对口；**仅用于候补段排序**，不进入主排序 |
| `source` | string | Agent 检索 | 报告链接 |
| `captured_at` | date | Engine 登记 | — |

- screener 现有「对话 Markdown 清单」**展示不变**，同时按本契约登记候选池
  （清单给用户看，登记给榜单消费——同一动作双输出）。
- 锚定铁律（借鉴天眼查 MCP）：简称/品牌名不得自行补全入库；
  先检索确认精确全称（尽量带统一社会信用代码），再登记。

### 2.2 公司档案 rating 回链

在 `companies/{canonical}.md` 分析摘要表新增（现有 city/industry/match_score/
risk_level 不变）：

| 字段 | 值域 | Producer |
|------|------|----------|
| `rating_tier` | recommend \| consider \| cautious | research Agent 生成（AI 推理） |
| `rating_caveat` | 保留条件（如"城市冲突+研发收缩"） | research Agent 生成 |

- 档案表值域兼容中文写法（推荐/谨慎推荐/可投/谨慎 → 引擎映射英文枚举）；
  溯源走档案 `source` 字段（已含 research + 日期），不单列 rating_by。
- 存量 4 家档案回填：从尽调决策的 company_rating 文本提取 tier + caveat
  （"推荐（有保留：…）" → recommend + caveat 括号内文本）。
- 决策文件中的 company_rating 文本保持不变（Record 是认知计算，不迁移重写）。

### 2.3 岗位线索 JobLead

| 字段 | 类型 | Producer | 说明 |
|------|------|----------|------|
| `id` | lead_{date}_{seq} | **Engine 登记** | 系统命名 |
| `company` | canonical 名 | Engine 关联 | 必须是已锚定公司 |
| `title` | string | company-jobs Agent 检索 | 岗位名 |
| `salary` | string? | 同上 | 检索不到显式标缺 |
| `city` | string | 同上 | — |
| `url` | string | 同上 | 来源链接（用户自行查看原文） |
| `source` | 官网 \| 招聘平台 \| 其他 | 同上 | 官网优先 |
| `captured_at` | date | Engine 登记 | — |
| `expires_at` | date | Engine 计算 | captured_at + 14 天；过期标「可能过期」 |
| `fraud_flags` | string[] | company-jobs Agent 判断 | 求职诈骗信号（§5.4） |

- **线索 ≠ 已递交 JD**：jobs/ 仍是「用户已递交 JD」唯一真相源；
  线索只存在于公司档案关联下，用户点击 → 粘贴 JD → 才进入 jobs/。
- 过期线索不删除，标记「可能过期，可刷新」；榜上提供「刷新线索」动作。

### 2.4 资质名单沉淀（knowledge 资产）

- 路径：`knowledge/资质名单-{城市}-{年份}.md`（如 `资质名单-城市A-2026.md`）
- 内容：小巨人 / 高新 / 瞪羚 / 独角兽名单表——`公司名 | 城市 | 资质类型 | 公示来源链接 | 批次年份`
- Producer：Agent 解析官方公示页（工信部/省工信厅/科技部门），**每条带来源链接**；
  年度刷新，非实时 API。
- 消费：screener 第 1 路资质信号先读沉淀名单，零搜索成本命中；未覆盖城市再走搜索。

## 3. 排序规则（确定性）

**榜单按城市分组罗列（分城市榜），城市不做排序因子——只做分组维度与段标注。**

### 3.1 分组：城市段

- 每个城市一个段（意向城市 / 冲突城市 / 其他城市 / 无城市信息），段内再排序
- 段顺序：
  1. **意向城市段置顶**（person.preference.city）
  2. 其余城市段排序规则（**一体两态，均为正式规则**，按数据可用性取用）：
     - 存在该城市的 city-advisor 评估 → 按评估适配度降序（与城市视图同源）
     - 不存在评估 → 按「段内最高 rating tier + 公司数」降序
     > 城市评估是**可选数据**，缺席是常态（用户可决定不跑，非异常场景）——
     两态都是确定性规则分支，不设 fallback 兜底。
  3. 无城市信息公司落「其他」段末尾
- 段头标注：意向城市 ✓ 徽标；冲突城市 ⚠ FLAG（提示不否决，沿用现有机制）
- **榜头跨城市洞察**（不替用户决策）：如「上海段 2 家 recommend vs 意向城市段 0 家——
  若接受搬迁，上海机会质量更高」；无评估数据时只做评级/数量的事实陈述对比，不臆测适配度

> 设计依据：城市是用户决策中的**待决策变量**而非已定事实（决策文件"城市决策前置"
> 模式）；分城市罗列让"坚守意向城市 vs 接受搬迁"的权衡显式可见，与城市视图语义一致。

### 3.2 段内排序（确定性，稳定排序）

同段内按因子顺序排列（同分保持次级因子顺序，最后按时间）：

| 序 | 因子 | 值 | 来源 |
|----|------|-----|------|
| 1 | **评级 tier** | recommend > consider > cautious | §2.2 rating_tier |
| 2 | **匹配因子加权** | JD 差距投影（引擎算）> 经历-场景契合（research 结构化）> 薪资可行（decision salary_feasible） | 详见 §3.3 |
| 3 | **风险信号** | risk_level + 求职诈骗 flags 降权 | 档案 + §2.3 fraud_flags |

- Tier 分层展示：**推荐 / 可投 / 谨慎**（映射 rating_tier + 风险降档）；
  **储备段**（无岗位无有效线索）与主排序段分开展示，不参与"投递顺序"。
- 城市冲突不再参与段内降档（已由分组+段标注承担），避免双重惩罚。

### 3.3 匹配因子口径收敛

现状两套匹配度并存（尽调 match_score 73% vs 引擎差距投影 52%），榜上只显示一套：

- **排序只用引擎差距投影**（Registration 级硬事实：SKILL_GAP/NOT_DECLARED/
  NEEDS_CONFIRMATION 计数与摘要）——可分解、可回源 JD、可产出升档前置条件
- `match_score`（AI 尽调推理）**不参与排序**；榜行以「尽调综合分」徽标并列展示，
  标注 AI 推理（保留其软性综合判断信息，不丢弃）
- 经历-场景契合：research 输出结构化契合条目（`场景 | 我的证据引用 | 契合度`），
  无结构化数据前该因子不计入且显式标注「待尽调结构化」，不猜测

**匹配因子按可用数据取子集**（数据可选状态建模，非兜底）：

| 公司状态 | 匹配因子计算 |
|---------|-------------|
| 已有已递交 JD | 差距投影 + 经历契合 + 薪资可行（全因子） |
| 无已递交 JD | 经历契合 + 薪资可行（子集），榜行显式标注「硬差距未计算——递交 JD 后可算」 |

> 无差距投影 ≠ 无差距。缺失因子的公司不惩罚也不加分，标注说明；递交 JD 后因子自动补全重排。

### 3.4 榜行排序理由透明

每个榜行必须能回答"为什么排这"：展开显示因子明细（tier、差距摘要、薪资对比、
风险）；城市 ✓/⚠ 属段头标注（§3.1），不在行内重复。**升档前置条件**结构化展示
（来自 rating_caveat 与决策中的前置条件，如「可投 · 前置：补核心选型认知 2-3 周」）。

## 4. 榜行 UI 契约

| 榜行字段 | 内容 |
|---------|------|
| 主信息 | 公司名（canonical）、城市、行业桶、评级 tier 徽标、排序因子摘要 |
| 岗位区 | 已递交 JD 数 / 有效线索数（展开岗位列表，含标题/薪资/城市/过期标记） |
| 状态联动 | 与投递看板同步：已投递公司显示「已投递 · 面试中/已拒」而非重复推荐 |
| 动作 | 见下 |

动作集合（按公司状态出现）：

| 动作 | 出现条件 | 行为 |
|------|---------|------|
| 投递 | 名下已有已递交 JD | 走现有投递闭环 |
| 去递交 JD | 有有效线索、无已递交 JD | 跳 JD 新增流程并预填公司名 |
| 刷新线索 | 线索过期或无线索 | 触发 company-jobs（批量可勾选） |
| 发起尽调 | 候选层（无 rating） | startAnalysis 预置 company-research |
| 重新评估 | 档案层 | 现有重新评估入口 |

- **空网格**：城市×行业无候选时显示「该城市×行业尚未筛选 · 发起公司筛选」
  （预置 company-screener prompt）——榜单同时是扩库引擎。
- **诚实标注**：榜头「已尽调 N 家 / 候选 M 家 / 覆盖网格 X/Y」；样本 < 5 时
  显式提示「样本少，榜单仅供参考」。
- 城市×行业矩阵视图（二维格子）为**后续可选**，一期不做。

## 5. company-jobs skill 契约（新增轻量）

### 5.1 职责与分工

- 输入：canonical 公司名（可批量，一次 ≤ 10 家）；输出：JobLead 清单（§2.3）
- 与 company-research 分工：research 的岗位段 = 尽调时快照；
  company-jobs = 按需刷新，只查招聘，不重复做业务/财务尽调。
- 与 jobs/ 分工：只产线索，不写 jobs/、不登记 roles.md（未分析岗位不进岗位清单）。

### 5.2 检索纪律（借鉴腾讯校招 skill）

1. **官网优先**：先查公司官网 careers/招聘页，其次主流招聘平台
2. **全量纪律**：禁止只看第一页；列表页翻全量（或等价全量）再本地过滤
3. **每条线索带来源链接 + 抓取日期**；检索不到显式标缺
4. **不编造**：岗位名/薪资必须来自检索结果；「服务不可用」与「该司无在招」
   表述严格区分

### 5.3 数据源双通道

- **通道 A（结构化）**：天眼查官方 MCP（`https://mcp.tianyancha.com/v1`，
  用户本地配置 API Key）——search_companies 锚定 → 招聘/榜单/风险相关能力发现调用
- **通道 B（降级）**：通用搜索（现有 WebSearch/Exa），信号驱动
- 双通道切换遵循降级纪律：通道 A 鉴权失败/限流/5xx → 通道 B；
  部分可用优先交付，标注缺的维度。**skill 不硬编码接口清单**（能力发现模式）。

### 5.4 求职诈骗信号（借鉴 fraud_checker）

线索检索时顺带识别风险信号：收费内推 / 保 offer / 培训贷 / 入职收费 /
私信加微信引流。命中 → `fraud_flags` 登记，榜行显示 ⚠ 提示（不自动否决，
最终判断归用户）。

## 6. 事件与刷新

| 事件 | 触发 | 榜单动作 |
|------|------|---------|
| 画像变化 | personsChanged（现有） | 城市分组/段顺序重算 + 匹配因子重算 → 重排 |
| 新 claim/evidence 确认 | 现有事件链 | 经历契合因子重算 → 重排 |
| 投递状态变化 | 现有投递事件 | 榜行状态联动 |
| 线索过期 | 14 天到期 | 标记「可能过期」 |

## 7. 二期预留：薪资基准知识层

- Schema 预留：`薪资基准-{城市}-{岗位}-{经验档位}.md` 表
  ——`来源 | 岗位 | 城市 | 经验档位 | P25 | P50 | P75 | 抓取日期`（Agent 检索登记，带来源）
- 个人估价卡输出契约：`市场估价 {区间}（P50，样本 N，日期）→ 你的期望 {值} → 报价建议 {合理/偏低/偏高 + 一句话依据}`
- 榜行薪资因子二期接入：岗位薪资 vs 个人市场估值（复用同一数据源）。
- 一期不实现，接口位置预留（榜行因子位 + knowledge 目录）。

## 8. 实施分期与 DoD

**一期**：
1. screener 候选池登记契约落地（skill 输出 + Engine 登记）
2. rating 回链（档案字段 + 存量 4 家回填）
3. 榜单模式 UI（三层 + 储备榜 + 动作集 + 诚实标注）
4. company-jobs skill（双通道 + 防诈骗信号）
5. 资质名单沉淀（格式 + 首次解析 1 个城市验证）

**DoD**：真实数据下完成一次「screener 捕捉 → 尽调 → 榜单排序 → 投递」全链
Playwright 实测；排序理由与因子明细可展开核对；空网格入口可触发预置 prompt。

**二期**：薪资基准 + 个人估价卡 + 榜行薪资因子。

## 9. 明确不做

- ❌ 客观公司排行榜（无可信数据源，且误导）
- ❌ Agent 自动抓 JD 入库 / 自动投递（投递与 JD 选择是用户事实）
- ❌ 新「捕捉+评分混合」skill（screener/research 分层已自洽）
- ❌ 榜单现场 AI 打分（排序必须确定性、可解释）
- ❌ 城市×行业二维矩阵视图（一期不做，作为后续可选）
