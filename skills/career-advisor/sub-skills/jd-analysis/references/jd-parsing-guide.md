# JD 深度拆解

从非结构化 JD 文本中提取结构化信息。显性需求 + 隐性信号 + Must/Nice分级 + 优先级。

---

## 一、结构化提取清单

### 1.1 基本信息

```
岗位名称: [原始标题]
          [标准化名称]（去掉花名，如"Java大神"→"Java开发工程师"）
薪资范围: [min]-[max] [月薪/年薪]
          [推断·是否合理]（对比行业基准）
工作地点: [省 市 区] or [远程/混合]
经验要求: [X-Y年] or [不限]
学历要求: [level] [硬门槛/偏好]
```

### 1.2 硬性门槛

| 门槛类型 | 判断规则 |
|---------|---------|
| 学历 | "要求"→硬；"优先"→软；"本科及以上"→硬 |
| 经验年限 | "X年以上"→硬；"有经验者优先"→软 |
| 专业证书 | CPA/律师证/注册工程师等→硬门槛 |
| 语言能力 | "英语可作为工作语言"→需验证实际水平 |
| 工作地点 | "必须base XX"→硬；"可远程"→软 |

与 career-transition 的硬门槛概念对齐：不满足则一票否决。

### 1.3 技能需求

分级采用 career-transition 体系。

```
必备技能 (Must-have):
  - [技能名] — 要求等级: [精通/熟练/接触过]
  - 提取依据: [JD原文引述]

加分技能 (Nice-to-have):
  - [技能名]
  - 提取依据: [JD原文引述]
```

判定规则：
- "精通/熟练掌握" → Must-have，要求等级=精通
- "熟悉/了解" → Must-have，要求等级=接触过
- "有XX经验" → Must-have，要求等级视上下文
- "有XX经验者优先" → Nice-to-have
- "加分项"/"preferred" → Nice-to-have

### 1.4 软技能信号

从 JD 措辞中提取，每条标注原文证据：

```
- [软技能] — JD证据: "[原文引述]"
  推断: [这个软技能在岗位中的实际含义]

示例：
- 跨部门协调 — JD证据: "推动研发、市场、销售团队协同"
  推断: 岗位涉及多部门利益冲突，需要影响力而非职权
```

### 1.5 职责拆解

```
职责 1: [描述] — 动词类型: [搭建/优化/主导/维护/执行]
        重要度: [高/中/低]（位置+具体程度）
        推断·核心KPI: [衡量标准可能是什么]
```

## 二、动词解码

### 开拓型

```
"搭建/创建/建立/从0到1/构建/打造"
  → 现在没有体系，需要你来建
  → 期望：有0-1经验，能在混乱中建立秩序

"开创/开拓/探索"
  → 公司或团队还没有这块业务
  → 风险：可能失败后岗位消失
```

### 优化型

```
"优化/提升/改善/改进/迭代/打磨"
  → 有体系但做得不够好
  → 期望：数据驱动，能发现问题并解决

"突破/攻坚/攻克"
  → 遇到瓶颈了，需要能解决难题的人
  → 风险：这个难题可能根本解决不了
```

### 管理型

```
"主导/牵头/统筹/带领/管理"
  → 需要跨团队资源整合能力
  → 期望：不是自己干，是推动别人干

"赋能/推动/驱动"
  → 互联网黑话，实际就是"帮助/推进"
  → 注意：这些词出现说明公司文化偏互联网风格
```

### 执行型

```
"负责/执行/完成/跟进/落实"
  → 既定流程中的操作执行者
  → 期望：执行力强、不出错
  → 成长空间：如果大部分职责都用这类动词，角色偏操作型
```

### 动词组合的含义

| 动词组合 | 岗位性质 |
|---------|---------|
| 搭建 + 主导 + 从0到1 | 创业/新业务，高风险高成长 |
| 优化 + 提升 + 迭代 | 成熟业务，需要改进而非重建 |
| 负责 + 执行 + 跟进 | 操作型岗位，稳定但上升空间有限 |
| 搭建 + 负责（矛盾） | JD质量可能不高，或角色定义模糊 |

## 三、优先级判定

### 按位置权重

```
JD 正文中：
  前3条职责 → 权重×3（日常工作的核心）
  前3条要求 → 权重×3（拿面试的硬条件）
  中间部分 → 权重×2
  最后部分 → 权重×1

JD结构不标准 → 按首次出现位置判定
```

### 按重复度

一个要求在JD中重复出现 → 提升一级（例：Important → Critical）

### 按具体程度

- 具体化程度高（有工具名/技术栈/场景/指标） → 真实需求，权重不变或提升
- 具体化程度低（"良好的沟通能力"、"较强的逻辑思维"） → 可能只是模板填充，降一级

### 最终分级

```
Critical（关键）: 权重×3 — 没有这个拿不到面试
  = 硬门槛 + 前3条职责对应的技能 + 重复出现 + 具体化程度高的

Important（重要）: 权重×2 — 有它优势明显，可入职后补
  = 非硬门槛但明确列出 + 中等位置 + 中等具体化程度

Supporting（辅助）: 权重×1 — 锦上添花
  = 加分项 + JD末尾 + 模糊的通用要求
```

## 四、隐性信号解码

### 团队与组织

| JD线索 | 推断 |
|--------|------|
| "汇报给[Title]" | Title越高→岗位越独立；Title越低→团队层级越多 |
| "你将加入一个[X人]的团队" | 明确数字=结构清晰；没提=可能很小或不确定 |
| "新增岗位" | 业务在扩张，好信号 |
| 没提新增也没提替代 | 面试时必须问清楚 |
| "独立负责"+"直接汇报给CEO/VP" | 可能是新增或扁平组织 |
| "跟[部门A、B、C]密切协作" | 处于多部门交汇处→沟通成本高但影响力大 |

### 业务阶段

| JD线索 | 推断 |
|--------|------|
| "从0到1"/"搭建"/"建立体系" | 业务早期，没有现成东西 |
| "优化"/"迭代"/"提升效率" | 有成型的，需要改进 |
| "规模化"/"复制"/"扩张" | 模式已验证，正在放大 |
| "扭亏"/"攻坚"/"攻克" | 遇到困难了，需要救火 |
| "维护"/"保障"/"稳定运行" | 成熟业务，保持运转即可 |

### 技术与工具成熟度

| JD线索 | 推断 |
|--------|------|
| 具体工具名+版本号 | 技术栈真实且具体 |
| 具体框架+场景 | 知道要做什么 |
| 列了一堆工具但无场景 | 可能是HR拼凑的 |
| 没提任何具体工具 | 岗位不依赖工具或JD太敷衍 |

## 五、红旗标注

### 高风险（面试必须追问）

- "抗压能力强"+"弹性工作制"+"快节奏"同时出现 → 大概率996+
- "薪资面议"+岗位职责模糊 → 薪资低且岗位定义不清
- 公司信息极少（无规模、无产品、无融资） → 可能虚假公司
- "急聘"+岗位已挂很久 → 矛盾信号

### 中风险（面试建议追问）

- 核心团队全部来自某大厂 → 可能存在派系
- "有挑战性"出现3次以上 → 可能前任因太难离职
- 技术栈描述和职责不匹配 → JD质量存疑
- 福利极其详细但薪资只字不提 → 用福利遮掩低薪

### 低风险（提醒注意）

- 互联网黑话密度过高 → 可能空谈大于实干
- 带过多修饰词 → 实际业务不如描述
- 岗位名称与职责不符 → Title通胀
