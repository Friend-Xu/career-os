# 证据创建（入口 A：主动沉淀）

> career-advisor 子模块（evidence）。由主 SKILL.md / AI 面板路由加载，不作为独立 skill 运行。
> 对应 M2 文档 `EVIDENCE-MODEL-M2-v0.1.md` §5 入口 A。输出契约：`evidence-output-schema.md`。

**用户说"我想整理一个项目经历" → 对话式引导 → 生成证据条目。**

不做填表，不做审核负担（H1/H2 教训）——一次对话问 3-5 个问题，能答多少答多少，半成品合法。

---

## 工作流

```
1. 确认事件 + 类型判定（先分类型，再引导——type 决定下游消费位置）
   "这次经历大概是什么？"
   "它是贯穿任职期的持续职责（日常维护/日常支持类），
    还是有明确起止的一次性专项（项目/交付类）？"
   → 判定标准见 evidence-output-schema.md「type 判定标准」（四信号）

2. 引导（按类型分轨）：
   独立项目（independent_project）六问：
     事件 → 角色 → 贡献 → 方法 → 验证 → 结果

   持续职责（professional_experience）四问：
     职责范围 → 持续期（哪段任职期内）→ 常规产出（规模/闭环，无数字不强问）→ 归属公司行

   分步问（每次一个问题，不要一次抛出整表）：
   - 你在里面是什么角色？
   - 你实际负责/做了什么？（这是贡献，不是岗位职责）
   - 用了什么方法或工具？
   - 怎么验证有效？（测试/评审/用户反馈…）
   - 结果或影响是什么？（指标变化、被采纳…）

3. 结构化落盘
   按 evidence-output-schema.md 生成
   写 evidence/{日期}-{事件名}.md
   status: candidate（未确认）
   source_type: user_input
   frontmatter 必写 type（按步骤 1 判定）+ owner；
   professional_experience 必写 work_row_ref（公司名+入职时间，与 identity 工作经历表一致）

4. 确认（可选，用户愿意时）
   "整理成这样，对吗？" → 确认 → 改写 status: trusted + verification
```

### 职责句拆分（v1.3，强制）

口述/素材中夹带的持续职责内容（如项目故事里的"顺便负责了日常维护"）→ **拆为独立的 professional_experience 证据**，不混入项目证据。一条证据一个类型，禁止混合叙事。

### 落盘时机（口述充分即落盘，不无限提问）

- **用户一次性口述已覆盖大部分六问信息 → 直接结构化落盘**，不要再逐个提问确认（H1/H2：逐问是负担）
- 只对**关键缺失**（如结果/验证完全没有）用一次提问补；提问无响应（用户跳过/不答）→ **以半成品落盘**（缺失维度省略，candidate 状态）
- 可推断的信息（口述"负责机械结构部分"→ 角色可标注）直接采用，不要为已可推断的信息提问
- 禁止为"凑齐六问"反复追问——缺什么省略什么，半成品合法

---

## 规则

1. **禁止编造**：用户没说"结果"就不填 impact；没说验证方式就不填 validation——半写状态合法，不强行补全
2. **一次一个问题**：分步引导，禁止一次抛出六个问题的表单
3. **role 是身份不是岗位责任**："机械结构负责人"是 role，"负责机架和传动模块设计"是 contribution
4. **内容自足**：口述内容完整写入文件，不依赖"简历第几页"这类会失效的引用
5. **重复整理同一事件**：照常写新暂存名文件，引擎自动分配新 ID（历史保留）
6. 文件写 `evidence/` 目录（不是 decisions/、不是 jobs/）
